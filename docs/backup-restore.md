# Backup and Restore

## What must be backed up

| Asset | Where | Why |
|---|---|---|
| Database | MySQL/MariaDB `DB_DATABASE` | every client, project, cycle, keyword, ranking, backlink, report, revision, audit event, import and migration record |
| Report PDFs | `storage/app/private/reports/` (or the S3 bucket when `REPORT_PDF_DISK=s3`) | final and archived report versions; they cannot be regenerated byte-for-byte |
| CSV uploads | `storage/app/private/imports/` | reviewable until pruned by `seo:prune-import-files` |
| Environment | `.env` | APP_KEY (without it encrypted data is lost), database and disk settings |

Source code is in Git and is not backed up; the deployed tag is recorded
in the deployment log. Legacy migration source workbooks live outside the
application and belong to the office's own file storage.

## Strategy (configurable, no provider assumed)

- Nightly `scripts/backup.sh` from cron (e.g. `15 1 * * *`), which writes
  `db-<stamp>.sql.gz`, `files-<stamp>.tar.gz` and a root-only `env-<stamp>.txt`
  into `BACKUP_DIR` (default `storage/backups`, mode 700).
- Local retention `BACKUP_RETENTION_DAYS` (default 14).
- A separate scheduled copy of `BACKUP_DIR` to another machine, the office
  NAS or object storage, with its own longer retention (suggested 90 days,
  plus one copy per month kept for a year because reports are contractual).
- Take an additional backup before every deployment and before any legacy
  migration `--apply`.

`scripts/backup.sh` uses `mariadb-dump` or `mysqldump` (whichever exists;
override with `DUMP_BIN`), `--single-transaction` for a consistent InnoDB
snapshot, and a temporary `--defaults-extra-file` so the password never
appears on a command line. Both MariaDB and MySQL clients accept these
options; `mariadb-dump` output restores into MySQL 8 and vice versa for
this schema (InnoDB, utf8mb4, JSON, no vendor-specific types).

On Windows/XAMPP hosts run the same steps manually:
`mysqldump --defaults-extra-file=<file> --single-transaction <db> | gzip > db.sql.gz`
and zip `storage\app\private`.

## Restore runbook

Restore replaces the current database and private files with the backup's
state. Anything entered after the backup is lost, so announce a
maintenance window and confirm the target is the right environment.

1. **Maintenance mode**: `php artisan down --retry=60`. Stop the queue
   worker: `sudo systemctl stop seo-queue` (or `supervisorctl stop`).
2. **Version compatibility**: the backup was taken with a given code
   version. Check out that tag (or a newer one whose migrations are
   additive) before restoring; never restore an old dump under code that
   expects columns the dump does not have without running `migrate --force`
   afterwards (step 6).
3. **Database restore** (creates a fresh schema; the current data is
   dropped, so make a last safety dump first):
   ```bash
   mysqldump --defaults-extra-file=<file> --single-transaction <db> | gzip > pre-restore.sql.gz
   mysql --defaults-extra-file=<file> -e "DROP DATABASE \`<db>\`; CREATE DATABASE \`<db>\` CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
   gunzip -c db-<stamp>.sql.gz | mysql --defaults-extra-file=<file> <db>
   ```
4. **Storage restore**: `tar -C <app-dir> -xzf files-<stamp>.tar.gz`
   (restores `storage/app/…`). Fix ownership:
   `chown -R <deploy-user>:<web-group> storage && chmod -R o-rwx storage`.
5. **Environment**: if `.env` was lost, restore `env-<stamp>.txt` as
   `.env`. The APP_KEY must be the one the data was written with.
6. **Migrations**: `php artisan migrate --force` (no-op when the dump
   matches the code; applies newer additive migrations otherwise).
7. **Caches**: `php artisan optimize:clear && php artisan optimize`.
8. **Queue**: `sudo systemctl start seo-queue`; `php artisan queue:restart`.
9. **Verification**: `php artisan app:production-check --production`;
   log in; open a project's Reports page and download a final PDF;
   `php artisan schedule:list`.
10. **Back online**: `php artisan up`.

Test a restore on a staging copy at least every quarter and after any
change to the backup script, database version or storage layout. A backup
that has never been restored is not a backup.

## Local restore smoke test performed

Verified on the development machine (MariaDB 10.4.32) with development
data only, never real client data: `scripts/backup.sh` (with
`DUMP_BIN=<xampp>/mysqldump.exe`) produced `db-*.sql.gz`, `files-*.tar.gz`
and the `.env` copy; the dump was loaded into a scratch database
`cp_seo_internal_tool_restore_test`, which then held all 45 tables (40
application tables plus framework tables) with row counts identical to the
source; the scratch database and the temporary backup were removed
afterwards. Repeat this rehearsal on the production server after
installation (`chmod +x scripts/backup.sh` first).
